# Read-only public study

- Only read public SIMplifica data. The only upstream POST allowed is `/api/resources/intervals`, a read-only availability query. Never book, pay, log in or change an account.
- Anonymous cookies and XSRF tokens stay in memory. Never log or persist request headers, cookies, credentials or raw service-page HTML.
- Public files contain generic code and public trail availability only. No names, email addresses, itineraries, user instructions, local paths or account identifiers. The GitHub repository owner is necessarily public.
- Collect all current Madeira-island booking-catalog resources, all returned slots and every non-resident percentage, including 0 and 100. Exclude Porto Santo before creating availability jobs, including on catalog fallback. Preserve route variants and exact source local timestamps with their IANA timezone. Keep older archives intact; derived analysis and official-status context cover Madeira only.
- Empty arrays, missing slots, schema errors, stale data and network failures are unknown, never inferred zero. Percentage is not a ticket count or proof of a booking.
- The exact generic title `0 vagas disponíveis` has no non-resident percentage. Retain its slot timestamps and null quota as `unreported`/`sourceSlots`, preserving any explicit percentages in mixed responses too. Exclude the uncertain resource/date from numeric analysis, mark comparison gaps, and continue the scan without retrying or tripping the source-error circuit. A completed scan may warn about this recognized source limitation without failing; other schema changes and actual failures must still fail visibly. Never infer a category percentage from the generic zero or capacity fields.
- Keep immutable compressed scans and their SHA-256 manifests. Never prune historical observations to reduce size. Stop with an explicit storage warning before the configured size guard instead.
- Reconcile a mid-scan withdrawal only after an additional verified live catalog removes an entirely rejected resource, without adding unqueried resources. Preserve the initial catalog and all rejected checks in catalogWithdrawal evidence. Never discard successful observations or change old archives; withdrawal is not proof of trail closure.
- Respect source rate limits; stop on 429 or an explicit Retry-After backoff and persist the cooldown. After a scan's first pass, allow only the configured bounded recovery of isolated transient availability errors: at most two delayed serial attempts per failed check, at most 20 affected checks. Never repeat successful checks, retry schema/authentication errors, bypass a circuit breaker/time budget or increase request speed. Keep attempt evidence and the successful retry's real timestamp; never repair older archives retrospectively.
- Apply the same at-most-two delayed retries to transient trail-catalog startup failures, its exact empty `e071` (Resource not found) rejection, and a catalog that contains only out-of-scope Porto Santo resources. Retain `catalogAttempts` and honor Retry-After. Availability queries require a freshly verified catalog with Madeira resources. A prior catalog may account for unknown coverage after failure, but must never authorize source queries while catalog verification is failing. A zero-check scan cannot succeed or establish a catalog withdrawal.
- Serialize collection runs and preserve the recent-complete-scan guard. Duplicate triggers must not create extra SIMplifica traffic or newer observation timestamps.
- The clock may dispatch one early replacement for the first GitHub startup failure in a sequence after verifying zero jobs and a five-minute delay. A replacement that also fails at startup preserves the original hourly deadline. Continued failures follow the regular interval.
- Publish by importing immutable evidence into current main and rebuilding derived reports there. Concurrent code/report commits must never require repeating source collection or overwrite historical scans.
- Use standard public Ubuntu GitHub runners, no Actions artifacts/caches, no LFS, no paid services. Only the built-in short-lived GITHUB_TOKEN may write generated data.
- The independent Cloudflare clock may use a separate repository-limited Actions-write/Contents-read credential, stored only as a Worker secret. No HTTP dispatch endpoint, account-specific configuration, credentials or paid add-ons belong in the public clock bundle.
- Keep the reporting reader aware of freshness and collection gaps. Hourly scheduling is best effort.
- Use one primary clock. Verify independent-clock operation by correlating a real Cloudflare scheduled event with its GitHub workflow_dispatch run. Successful manual runs do not establish automatic operation. If native GitHub cron is restored, register it with an active maintainer's public GitHub identity and noreply email, then verify an actual schedule event. Use bot authorship for generated observation commits.
- Analysis must distinguish first-seen low availability from observed threshold crossings, mark gap-spanning intervals, exclude observations after slot entry, and count distinct visit dates rather than repeated hourly checks as independent samples.
- Run `npm test` and `npm run verify` after changes. Validate the live anonymous flow when changing upstream access. Keep README and analysis limitations accurate; commit and push completed authorized changes.
